THE MENTAL MODEL

There is exactly one idea in this system.

state = fold(events)

The log is the system of record.

Supplier statements are appended, never updated in place. Anything you see published — a name, a barcode, a merge — is derived, never stored as truth.

Pure functions, no processes.

No GenServers, no runtime state, no database in the core. Every module is data in → data out. If you can run mix test, you can run the whole engine.

Bugs become recomputations.

A wrong answer is never patched — the rule is fixed and the projection is re-folded from the log. That's why explainability and undo come for free.

THE PIPELINE

Supplier history in, golden records out — four stages.

lib/ingest/envelope_loader.exspec: docs/HISTORY_ENVELOPE.md
Parse & validate the HistoryEnvelope — a supplier's full delta history in the contract-C shape. Garbage stops here.
lib/ingest/claim_mapping.exspec: docs/CLAIM_MAPPING_SPEC.md
Fold listings into engine claims — canonicalize codes, partition into periods. This is where "supplier says" becomes structured evidence.
rederive.ex · temporal.ex · finer_claims.ex
Cluster & reconcile — claims sharing authoritative codes collapse into one identity, as dated identity events. Merges and splits fall out of the data.
lib/ingest/golden_records.ex
Project the golden record — the whole-product view we publish, with survivorship decided by an injected policy (medipim_policy.ex).

Each stage is a pure function with its own spec and its own test file. You can understand — and change — one stage without holding the rest in your head.

VOCABULARY

Six words carry the whole domain.

claim

One supplier asserting "this entity carries this code, over this period." The atomic unit of evidence — never edited, only superseded.

code · code set

A typed identifier (national code, GTIN, ISBN…) after canonicalization. Authoritative codes prove identity; weak ones (bare barcodes) only suggest it.

cluster

Entities provably the same product because their claims share authoritative codes. Computed, never hand-assigned — merges and splits are just the cluster changing.

golden record

The published projection of one cluster: best value per field, with provenance. Recomputable from the log at any date.

lane

A per-kind content stream — photos, descriptions, documents, ingredients. Same ledger, same rules, applied beyond scalar fields.

steward verdict

A human decision recorded as an event, for cases the engine refuses to guess (a shared barcode, a suspicious merge). First-class evidence, not a DB override.

These names are used identically in the specs, the Elixir code, the PHP code, and the tests. When you talk about the system, use them.

THE REPO

Three projects, one truth.

lib/golden_record_core.ex — the engine
  15 flat modules, ~2,000 lines, one file
  Codes · Cluster · IdentityLedger · Catalog · History…
lib/ingest/ — the medipim pipeline
test/ — 363 ExUnit tests, real fixtures
docs/ — the specs (they lead, code follows)
php/ — the parity port (own composer project)
api/ — HTTP + Postgres (own mix project)

Zero dependencies, on purpose.

The root project is stdlib-only — the built-in JSON module, no Jason, no Ecto. Clone, mix test, done. Adding a Hex dep is a decision, not a default.

The engine knows nothing about medipim.

Supplier-specific scoring lives in medipim_policy.ex and is injected as a rank function. New market or supplier = new policy + config, engine untouched.

Specs are the contract.

HISTORY_ENVELOPE.md and CLAIM_MAPPING_SPEC.md define behavior; spec tests pin the code to them. A behavior change starts as a spec edit.

TWIN ENGINES

Every change is made twice — and proven identical.

Elixir — the reference

Where design happens. The whole engine in one readable file; the full suite runs in half a second, so you iterate at thinking speed.

Change here first, with a test that pins the new behavior.

PHP — the production twin

Where it ships. A faithful port that runs inside today's platform — same modules, same names, same answers.

Port the change second, mirroring the Elixir diff class-for-class.

parity.ex and shared snapshot fixtures compare the two engines' output on real product histories. If your port drifts by one byte, CI tells you — not a customer.

RULES OF THE ROAD

Four invariants. Everything else is negotiable.

1

Never erase an event.

Corrections are new events (retractions, verdicts) — the log only grows. If your diff deletes or mutates history, it's wrong by construction.

2

Keep the core generic.

Supplier and market knowledge lives in injected policies and config, never in the engine. If you're writing if medipim in the core, stop.

3

Both engines or neither.

An Elixir change without its PHP twin doesn't merge. Parity snapshots are the referee — keep them passing, never "adjust" them to make a diff go green.

!

ClaimMapping changes ripple into three suites.

Claim-count pins live in the spec tests, the parity snapshots, and api/test/e2e_migration_test.exs. Run the api suite locally before pushing such a change.

TEST DATA

We test against real product histories, not toys.

entity 422156 · Belgium

The full delta history of one real medipim product, checked in as a fixture. gen_422156.exs regenerates the decoded envelope from the raw dump — the fixture is reproducible, not sacred.

entity 347025 · France

Pins the pipeline cross-language: a second market's coding scheme, exercised end to end in both engines.

books · ISBN

A whole different domain through the same engine — proof that the core is generic, not pharma-shaped. See books_adapter.ex.

Australia · 127,000 entities

A full national export ingested with configuration only — new code schemes, GTIN migrations, shared barcodes. The stress test for "a market is a config table."

When you change behavior, these fixtures are what catches you. If a pinned claim count moves, you must be able to say why — the diff is the review.

GETTING STARTED

Your first week, in four moves.

1

Watch it work.

Run mix run golden_record_ddd.exs and read what it prints — the whole story from supplier claims to a golden record, on real data.

2

Read the story as tests.

test/walkthrough_test.exs and test/ingest/ingest_walkthrough_test.exs narrate the system as executable assertions.

3

Read the two specs.

HISTORY_ENVELOPE.md, then CLAIM_MAPPING_SPEC.md. They're short, and they are the contract everything else obeys.

4

Make one change, twice.

Pick a small issue. Elixir first with a test, then the PHP twin — and let the parity suite prove you got it byte-identical.
