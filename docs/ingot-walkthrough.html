Ingot

Golden records from contradicting sources.

Products carry many codes — GTIN, CNK, MPN, supplier refs — and the sources that assert them disagree. Ingot keeps every claim, folds them into one record, and refuses to invent a winner when the evidence is genuinely split.

Section one

The log

Nothing in Ingot is stored as a current value. There is an append-only sequence of claims, and every answer is a fold over it. Get this one idea and the rest of the system follows.

01 · The log

The log is the system of record

# A projection is never stored. It is computed. golden_record = log |> Enum.filter(&known?(&1, known_at)) |> Enum.filter(&effective?(&1, effective_at)) |> Substrate.current() # last-wins per slot |> Cluster.variants() # codes -> identities |> Catalog.project(priority) # resolve contradictions
Why this matters for everything else

Because the answer is recomputed, you can ask it as of any point in time, replay it after a bug fix, and rebuild every database table from scratch. Read models are a cache, never a truth.

Three consequences
  1. 01Corrections are appends You never mutate history. A wrong fact is superseded by a later claim, and the wrong fact stays visible in the audit trail.
  2. 02Determinism is testable Same log in, same record out. Order-independence is asserted directly in the suites — equal-priority ties sort by (rank, source, value).
  3. 03Two clocks become possible Because nothing is overwritten, "what did we know in March?" and "what was true in February?" are different filters over the same log.

01 · The log

Claims: the atom of the system

A claim is one source saying one thing at one time. It is never a command and never authoritative on its own — it is evidence. Seven kinds cover everything the engine models.

KindSaysUsed for
identityThis listing carries these codes. The clustering input. Codes bridge listings into one identity.
attributeThis code has field = value. Names, weights, dosages — anything survivorship resolves.
mediaThis asset depicts this code. Images, with a primary/secondary role.
groupingThis code belongs to legacy product N. Continuity with the system being replaced.
edgeThis code relates to that code. The typed graph: contains, describes, depicts, suppress.
member_ofThis code is in that collection. ATC groups and similar namespaces.
identity_evidence These two codes are / are not the same thing. The escape hatch. How a human overrules the clustering rules — covered in section two.

01 · The log

Slots, and why last-wins is not lossy

Every claim computes a slot — a tuple identifying exactly which fact it is asserting. Within one slot, the newest claim from that source wins. Across sources, nothing wins yet: all of them survive into survivorship.

# the slot is derived, never supplied def slot(%ClaimAsserted{source: s, kind: :attribute, data: %{code: c, field: f}}), do: {s, :attr, c, f} # manufacturer's weight and supplier's weight are # DIFFERENT slots. One does not overwrite the other. {"manufacturer", :attr, {:gtin, "054100…"}, "weight_g"} {"supplier", :attr, {:gtin, "054100…"}, "weight_g"}
→

Within a source

Last write wins. A supplier correcting its own weight replaces its previous claim — that is an update, not a disagreement.

↔

Between sources

Nothing is dropped. Two sources on the same fact are a contradiction, and contradictions are the whole point of the system.

The distinction is structural

Because source is part of the slot key, the engine cannot accidentally silence a disagreement by treating it as an overwrite.

01 · The log

Source records: four operations

Claims do not arrive one at a time. Upstream systems own whole records, addressed by {source, ref} and revised atomically. Each revision names the operation it is performing, and the engine enforces which operations are legal from which state.

01

replace

The whole record, as it now stands. Anything the payload omits is gone — omission is a deletion, not a silence.

The only legal first revision.

02

patch

Change only the named facts. Everything unmentioned is preserved. Explicit removal needs an explicit selector in remove.

Legal only on an active record.

03

withdraw

The record contributes nothing from now on. It is not deleted — the log keeps it, and its surrogate key is held, not recycled.

Rejects any claims or remove selectors.

04

reactivate

A withdrawn record comes back with a fresh whole record. It reclaims its old key — even if every code changed.

Legal only on a withdrawn record.

01 · The log

Two rules that make replay safe

Rule one
Store the result, never the delta

A patch event does not record "change the weight". It records the complete resulting snapshot of the record after the patch was applied.

Replay never depends on the future

If the patch algorithm changes next year, replaying a two-year-old log still produces exactly what it produced then. A stored delta would be reinterpreted by the new code; a stored snapshot cannot be.

The cost is storage. The benefit is that history means one thing forever, which is the entire premise of an event-sourced master-data system.

Rule two
Every revision passes a gate
ResultWhen
replay Same revision id, same content fingerprint. A no-op, not an error — retries are safe.
409 Same revision id, different content — someone reused a version number. Also an illegal transition: a first revision that isn't replace, patching a withdrawn record, reactivating a live one.
412 base_revision does not match the current revision. Optimistic concurrency: you were working from a stale copy.
422 Malformed: a bad address or interval, a withdraw carrying claims, or an active record without exactly one identity claim holding at least one code.

The fingerprint is a SHA-256 over the address, operation, claim identities and interval — so idempotency is content- based, not a client-supplied token.

Section two

Identity

Deciding which listings are the same product is the hardest thing the engine does, and the place where being wrong is most expensive. Ingot's answer is to be cautious by default and to make every override an event.

02 · Identity

Codes bridge listings into identities

Take every live identity claim, treat its codes as a set, and join any two sets that share a code. The connected components are the identities. That is the whole algorithm — and then reality complicates it three times.

i

Shared codes never bridge

Some codes are legitimately carried by many distinct products — a shared packaging code, a generic reference. Marked shared, they stay members of a cluster but are not allowed to fuse two clusters together.

A steward can declare a code shared with a ConflictResolved decision; the ingest also restricts known ones.

ii

Established keys never auto-merge

If a new bridge would join two clusters that already have surrogate keys, the engine does not merge them. It emits a merge proposal and waits for a human.

Auto-merging two live products is the one mistake that is genuinely hard to undo downstream.

iii

Unique ids can veto a bridge

If joining two components would put two different national-grade ids — CNK, ISBN — into a single identity, the bridge is held.

This is the case on the next slide, and the most interesting thing in the engine.

Lanes: four kinds of thing, four ledgers

A product, the substance inside it, the text describing it and the photo of it are different entities that happen to travel together. Each lane clusters independently, in its own ledger, with its own key prefix.

LanePrefixSchemes that route here
productSK_1 The default. gtin, cnk, isbn, mpn, supplier_ref — every scheme not listed below, so pre-lane logs keep their meaning.
substanceSUB_1 cas, unii, substance_id
descriptionDSC_1 text_id
mediaMED_1 asset_id
(neutral)— uuid is lane-neutral. A claim made only of uuids must name its entity explicitly.
One claim, one lane

Codes from two lanes in a single identity claim are a contract violation, not a guess to resolve. A thing cannot be a product and a substance at once.

Lanes are joined by edges, not by fusion

Each relation declares which lanes its endpoints may occupy, so traversal is scoped config rather than blanket closure:

containsproduct → substance
describesdescription → product, substance
depictsmedia → product, substance
suppressdescription → product

Without signatures, one common excipient would drag its descriptions onto thousands of unrelated products.

02 · Identity

The ledger, and the life of a key

Clusters are recomputed on every fold, but surrogate keys must be stable — downstream systems store them. The ledger is the memory that maps a cluster back to the key it already had.

  1. →IdentityMinted A cluster with no existing key gets a fresh one.
  2. →IdentityMembersChanged The key survives; its code set moved.
  3. →IdentitiesMerged Two keys become one — only ever from a steward decision, never automatic.
  4. →IdentitySplit One key breaks apart. Which side keeps the key is decided by has_spine?/1 — see the next slide.
  5. →IdentityRetracted Every contributing listing was withdrawn. It carries the last known codes, so the notification can say what was lost.
Keys are held, never recycled

A retracted SK_7 does not free up the number 7. A later unrelated record gets SK_8. Reusing an identifier that a downstream system still remembers is worse than leaving a gap.

Merges leave standing evidence

When a steward approves a merge of two conflicting national ids, the engine also writes identity_evidence: same for that pair. Without it, the very next replay would re-apply the unique-id guard and split back apart what the human just joined.

That detail is a good test of whether you have internalised the model: a decision that isn't in the log didn't happen.

02 · Identity · the hard case

Two CNKs arrive on one barcode

A national id is supposed to be unique per product. A barcode is supposed to identify one product. Here they contradict each other, and both cannot be right.

# supplier A's listing {:gtin, "05410013100072"} {:cnk, "1234567"} # supplier B's listing {:gtin, "05410013100072"} <- same barcode {:cnk, "7654321"} <- different CNK
The naive answer is wrong

Plain connected components joins them on the shared GTIN and produces one identity carrying two national ids. That record is silently corrupt: it will be published, consumed, and stored downstream before anyone notices.

What Ingot does instead
  1. 01Hold the bridge The union-find refuses the join. Two separate identities remain, each internally consistent.
  2. 02Flag the contradiction A ConflictFlagged event names the held code, so the barcode is visible as the thing in dispute.
  3. 03Keep serving Everything unrelated to this barcode is unaffected. One contradiction does not degrade the rest of the catalogue.
The exception that proves it

If one source record asserts both CNKs together, that is a deliberate statement that they are aliases — positive evidence, not a collision. The pair is never held again.

Why, and what it costs

has_spine?/1 is literally "does this cluster contain a GTIN", and it decides which side keeps the surrogate key on a split. The registry already grades a barcode as a suspect bridge — but nothing consumes that grade.

The four reasons are not one event

Used on a different pack — an effective-time boundary.
Incorrectly recorded — a known-time correction; the old link was never true.
Merger / takeover — a supplier attribute. Identity must not move at all.
Invalidation / ended — valid_to with no successor.

The machinery already exists

Given valid_to on the old association, the projection answers one identity before the transfer date and two after — both correct. An ingest obligation, not a redesign.

02 · Identity

Overruling the rules, on the record

Automatic rules will be wrong sometimes. The design question is not how to avoid that — it is where the override lives. In Ingot it is a claim in the log, not a flag in a database or a special case in the code.

same

Force a join the guard would refuse

A trusted source asserts that two codes name the same thing. The bridge is allowed even though it puts two national ids together.

Where it comes from: a steward approving a merge, or an upstream system with authority to say so.

Why it must persist: it is re-read on every fold. The override survives replay because it is part of the history.

distinct

Forbid a join that looks fine

Two codes that share a bridge are declared to be different things anyway — a mis-keyed barcode, a recycled reference.

Effect: the components stay apart no matter how much evidence accumulates for joining them.

Trust boundary: only sources in the trusted set are read as evidence. Ordinary suppliers cannot assert it.

Section three

Truth

Once you know which product it is, you still have to say what it weighs. Four sources, three answers. Ingot resolves what it can with a priority list — and returns nothing at all when it can't.

03 · Truth

Survivorship, and the refusal to guess

How a field is decided
  1. 01One entry per source Within a source, the latest claim for that slot.
  2. 02Rank by priority A configured per-field list, e.g. manufacturer before supplier for name, with a default list behind it.
  3. 03Look at the top tier only If every source at the winning rank agrees, that value is the answer: status: resolved.
  4. 04Otherwise, stop Distinct values at equal rank means status: needs_review — and value and winner are both nil.
This is the change most likely to surprise a consumer

Earlier versions returned the top-ranked candidate even when the decision was contested. A caller reading .value unconditionally now gets nil on contested fields and must check status.

The argument for it is simple: a plausible guess presented as a fact is worse than an absence, because nothing downstream can tell it was a guess. The candidates are still returned — the caller can see exactly who said what and decide for itself.

# contested field, priority cannot separate them %{value: nil, winner: nil, status: :needs_review, candidates: [{"manufacturer", 300}, {"supplier", 305}]}

Ties are broken by (rank, source, value), so two runs over the same log always order the candidates identically.

Section four

Two clocks

"What did the record say in March?" and "what was true in March?" are different questions with different answers. Most systems conflate them. Keeping them apart is the reason this rebuild happened.

04 · Two clocks

Known-at and effective-at

A correction received in April can say a product name was wrong for one week in February. Both facts are true simultaneously, and a query must be able to ask for either.

ClockQuestion it answers
known_at What information had reached Ingot by this moment? An RFC3339 timestamp assigned by the server. Clients cannot choose it.
effective_at What did the sources say was true on this date? An ISO date, supplied by the source, describing the world rather than the system.
The audit property

Asking with a March known_at returns the old answer even after the April correction exists — because in March, Ingot had not received it. That is what makes the history defensible rather than merely stored.

known_at = 2026-03-15 before the correction
FEB
MAR
APR

Returns the original name for every date. The correction does not exist yet.

known_at = 2026-04-20 after the correction
FEB
MAR
APR

Returns the corrected name for that one week in February, and the original everywhere else.

GET /v1/products/422156 ?known_at=2026-03-15T00:00:00Z # the system clock &effective_at=2026-02-10 # the world clock

04 · Two clocks

Half-open intervals, and why order matters

valid_from ≤ date < valid_to

Every fact carries an interval. It is half-open: inclusive at the start, exclusive at the end. Two consecutive intervals meet exactly once, with no gap and no overlap, and valid_to: null means "still applicable".

Why half-open, always

Inclusive-end intervals force every consumer to decide whether a boundary date belongs to the old fact or the new one — and different consumers decide differently. One convention, enforced at the contract, removes an entire class of off-by-one disputes.

Selection happens before clustering

This is the subtle part. The projection does not fold the whole log and then filter. It:

  1. 01Filters to what was known at the requested timestamp.
  2. 02Collects every valid-time boundary in that set, up to the requested date.
  3. 03Walks the boundaries in order, re-reconciling identity at each one, so keys evolve the way they actually evolved.
What that buys

A future-dated revision cannot hide the record that currently applies, and a bounded withdrawal hides a record only inside its interval — the prior revision reappears on either side.

Section five

Stewardship

The engine deliberately leaves decisions unmade. Somebody has to make them — and the system has to be able to prove who decided what, on what evidence.

05 · Stewardship

A decision is bound to the evidence for it

Four-eyes approval is easy to implement badly: count two clicks, apply the change. That is not enough, because the world moves between the two clicks.

01

Open the case

A conflict produces a case that snapshots the exact members, claims and event offset the steward is looking at — then hashes it.

The case is state in the log, not memory in a web session.

02

Endorse it

Each endorsement names the authenticated principal — taken from the credential, never from a name in the request body — plus the offset they saw.

Two distinct principals are required for a merge, split or suppression. One suffices for an attribute pick.

03

Recheck, then apply

The second approval recomputes the scoped evidence under the writer lock and compares digests. Unrelated events may have advanced the log — that is fine.

Changed evidence makes the case stale and the decision is refused. You approve what you actually saw.

Section six

The service

A pure fold is a lovely thing that cannot answer an HTTP request in millisecond time. Everything from here is about making the fold fast without letting it stop being the truth.

06 · The service

One log, twelve disposable tables

Authoritative
The event log

Append-only, stored as jsonb — not an opaque binary blob. You can read the history with SQL, and the payload does not depend on a serialisation format that only one language understands.

recorded_at is a real timestamptz; valid_from and valid_to are real date columns. The two clocks are indexable, not buried in JSON.

The test that keeps it honest

"Rebuilding from the event log reproduces records, tombstones, and key bindings." If that ever fails, a read model has quietly become a source of truth.

Disposable
The read models

Twelve indexed tables — golden records, identity members, code ownership, redirects, current claims, review cases, tombstones, source-record views and more. Every one can be truncated and replayed.

They replaced a single serialised state snapshot. The snapshot was simple but had to be rewritten whole; these are queryable, so legacy-id resolution is a recursive CTE walking the redirect chain instead of a fold in application memory.

The rule that makes it safe

Nothing here is authoritative. If a projection is wrong, you delete it and rebuild — you never repair it in place, because there is nothing to repair against.

Closing

Where it stands, and what is next

Ingot is a production-pilot-shaped POC, not a live service. The engine and the API are done and green; the remaining work is displacing the system it replaces.

The cutover chain

Strictly sequential — each phase is blocked by the one before it. And as of today the first one is blocked too.

P1Claim-mapping spec — every legacy field, plus the translator into engine claims. Now blocked on the barcode key-stability fix — writing the mapping first would bake the bug in.
P2Whole-product parity harness, at scale
P3Close parity gaps until divergences are zero or explained
P4Backfill, identifier lifecycle, search index — still shadow
P5Cut over reads
P6Cut over writes, retire the delta machinery
Everything on the right is written down, not quietly carried

Which is the same instinct as needs_review — applied to the codebase instead of the data.

Known debts
A grade with no consumer — P0

The barcode bridge grade is defined and documented as suspect, but nothing enforces it, and has_spine?/1 lets a surrogate key follow a transferred GTIN. Slide 15.

A seam with no producer

The runtime scheme registry is implemented, validated and tested — but nothing loads one. Every production path passes nil. Either wire it to a config file or remove the threading until something needs it.

A heavy runtime image

Based on postgres:16-bookworm just to get psql — a whole database server shipped for one client binary.
